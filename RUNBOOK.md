# Что запустить на своём железе (runbook)

Короткая версия: на любой машине с Python 3.11 решение работает из коробки. Тестовая часть (269 чипов:
180 AF + 89 BS) считается **≈10–12 с на 6-ядерной машине** и **≈35 с на двух ядрах** при лимите 30 с на прогон —
поэтому на своей машине ставьте пул по числу потоков (`--jobs 12` для 6 ядер и 12 потоков), либо переключайте
режим BS на пороги (тогда ≈7 с):
в `weights/weights.json` замените `"bs_mode": "model"` на `"bs_mode": "thresholds"`. Цена переключения — 0.029
Score на отложенной части.

Ниже — полный порядок действий: от установки до проверки сабмита.

---

## 0. Что нужно

| Ресурс | Минимум | Комментарий |
|---|---|---|
| Python | 3.11 | проверено на 3.11, работает и на 3.10 |
| Ядра CPU | 2 | `inference.py` сам поднимает пул `min(4, ядра)` процессов |
| ОЗУ | 4 ГБ | один чип BS (512×512×13) занимает десятки МБ |
| Диск | ≈6 ГБ | 2.2 ГБ train + 2.2 ГБ распаковка + ≈1 ГБ тест |

| GPU | не обязателен | обучение модели степени поражения ускоряется на NVIDIA (CUDA) через `xgboost`; инференс и так параллелится по ядрам |

python -m pytest tests -q              # 82 тест, ≈25 с — проверка, что окружение живое
```

## 1. Данные

**Тестовая часть** (`fire-test-renamed.tar` ≈ 878 МБ) — то, что открывается на платформе. Внутри архива
каталог `test/` с `af/`, `bs/`, `meta.csv` и `sample_submission.csv`; масок и геопривязки нет.

Куда положить: **в любое место вне репозитория** — `--data-dir` указывает на каталог с чипами (то есть на
`test/` из архива или на его родителя — решение само спускается на уровень ниже, если чипов в указанном

# 2) и сразу ответ
cd solutions/fires-monitoring
python -m fires.chips --data-dir ~/firesdata/test                 # диагностика раскладки
python inference.py --data-dir ~/firesdata/test --output submission.csv --validate
```

Ожидаемая раскладка после распаковки (если делаете руками — `tar xf fire-test-renamed.tar -C ~/firesdata`

├── af/  (viirs/, aux/, images/)          AF-чипы без масок
├── bs/  (sentinel2_pre/post, sentinel1_pre/post, aux, pre, post, sar_pre, sar_post)
├── meta.csv
└── sample_submission.csv    ← 447 строк: по одной на AF-чип (class_id=1) и по три на BS-чип (1/2/3)
```

Проверки, которые стоит сделать глазами: в `sample_submission.csv` **447 строк** без заголовка (180 AF +
3 × 89 BS), каталогов `masks/` нет — `--validate` всё это проверит сам, но полезно знать ожидаемые числа.

**Репетиция до/вместо теста** — макет теста из обучающей части (чипы без масок + шаблон организаторов):

**Обучающая часть** — если её нет под рукой, скрипт заберёт те же архивы из репозитория команды:

```

Проверка, что раскладка распознана (печатает каналы, маски и число чипов):

```

**Если решение говорит «не нашлось ни одного чипа»** — это путь или раскладка, а не данные. Что делать:

```cmd
dir /b %USERPROFILE%\Documents\cosmo1\train
dir /s /b %USERPROFILE%\Documents\cosmo1\*meta.csv
dir /s /b %USERPROFILE%\Documents\cosmo1\*.rar
py -3 -m fires.chips --data-dir %USERPROFILE%\Documents\cosmo1\train
```

* в папке только `.rar` — обучающая часть ещё не распакована: ПКМ по `...part001.rar` → «Извлечь в текущую

* `meta.csv` нашёлся глубже (`...\train\train\meta.csv`) — распаковывать заново не нужно: `train.py`,

* для обучения нужен каталог с масками: если указать тестовую часть, решение скажет «нет BS-чипов с маской
  степени поражения» — это ожидаемо, обучать на тесте нельзя.

## 2. Диагностика и обучение

### 2.0. Диагностика перед перебором (≈5 мин, без обучения)

Перебор из 17 шагов имеет смысл только когда известно, где теряется Score. Сначала —
замеры на текущей конфигурации из весов (предсказания тем же кодом, что инференс):

```bat
rem что путается, где FP/FN по покровам, что режет ROI-гейт, влияние облаков, худшие чипы
py -3 tools\diag_errors.py --data-dir <путь>\train
rem быстрый срез порогового пути без модели (секунды вместо минут)
py -3 tools\diag_errors.py --data-dir <путь>\train --thresholds-only --limit 60
```

Как читать вывод:

* **раздел 1 (confusion)** — если главный провал 0↔1, резерв в границе «гарь/фон»
  (ROI-гейт, веса трудных отрицательных, бинарная голова), а не в классах 2/3;
* **раздел 2 (покровы)** — на каких покровах FP и пропуски класса 1/2; точечные фиксы
  (порог, вес, морфология) применяются туда, а не на весь чип;
* **раздел 3 (ROI)** — строка 0.05 показывает, сколько истины каждого класса модель
  вообще не видит; если режется много класса 1 — кандидат № 1 на ослабление гейта;
* **раздел 4 (облака)** — просадка на облачных чипах чинится маской/SAR, а не моделью;
* **раздел 6 (худшие чипы)** — ручной разбор 2–3 чипов через `tools\inspect_chip.py`
  обычно даёт больше, чем ещё один перебор гиперпараметров.

Проверка, что оценка считает именно ту конфигурацию, что заявлена (режим AF/BS,
загрузка модели и фильтра печатаются явно; `--strict` останавливается, если файл
весов требует модель, а она не загрузилась):

```bat
py -3 evaluate.py --data-dir <путь>\train --strict
```

Важно про сплит цикла: веса собраны на каноническом сплите (`--val-frac 0.25`, сид
по умолчанию), и ID чипов каждого прогона теперь сохраняются в `docs\severity_loop.json`
(раздел `split`). Запуск с другим `--val-frac`/`--seed` делает точку отсчёта из весов
несравнимой (часть val входит в её обучение) — цикл сам предупредит об этом строкой
«ВНИМАНИЕ» и пометит вердикт как смещённый. Честный отбор — только на том же сплите,
что и веса.

### 2.1. Обучение (нужно один раз; ≈30–60 мин, на 2 ядрах дольше)

```bash
python train.py --data-dir /tmp/firesdata/real/train --out weights/weights.json
```

`train.py` делит набор по событиям пожара (`fire_event_id`) и проходит четыре стадии:

1. **AF** — 108 конфигураций порогов плюс обученный классификатор очагов (отсев факелов и блика);
2. **BS** — 64 тройки порогов dNBR по группам покрова, затем восстановление гари под облаком по
   Sentinel-1 и выбор сглаживания dNBR (по двум фолдам);
3. **модель степени поражения** — градиентный бустинг на 23 признаках пикселя (dNBR, rdNBR,
   NDVI/NDMI, каналы, покров, рельеф, VV/VH и контекст; флаг `--features ext` добавляет ещё 17 —
   видимый диапазон, влажность B11/B12, рельеф, текстуру dNBR и сезон); обучается на подвыборке
   пикселей (4 000 на чип, ≈670 тыс. строк) и **принимается только если обыгрывает пороги** на
   отложенных чипах, иначе решение остаётся пороговым. Устройство обучения — флаг
   `--device auto|cpu|cuda`, бэкенд — `--backend auto|sklearn|xgboost` (на GPU доступен только xgboost);
4. **морфология режима модели** — чистка мелких контуров и заполнение дыр подбираются отдельно
   (модель различает дыры внутри гари, поэтому их не заполняют).

На выходе: `weights/weights.json` (пороги + `bs_mode`) и `weights/severity_model.pkl` (модель
степени поражения). Веса уже лежат в репозитории — этот шаг нужен, если данных стало больше,
другой регион или хочется повторить подбор у себя. Обучение детерминировано: тот же датасет и
`--seed` дают те же числа (сид по умолчанию 20260918).

### 2.2. Цикл обучения модели степени поражения (17 шагов, «стало лучше или нет»)

Модель степени поражения — единственная обучаемая часть решения, и именно она даёт основной прирост
Score. `train.py` перебирает всё сразу (≈20 минут), поэтому для итераций по модели есть отдельный
скрипт: он делает 17 проходов, на каждом обучает одну конфигурацию, считает метрики соревнования на
отложенных 56 чипах (по событиям пожара, как в `train.py`) и печатает вердикт.

```bash
# полный цикл (≈15–40 мин на CPU, быстрее на GPU)
py -3 tools\train_loop.py --data-dir %USERPROFILE%\Documents\cosmo1\train --device auto --save

# тот же цикл, но с защитой от подгонки под валидацию: берём только подтверждённые улучшения
py -3 tools\train_loop.py --data-dir %USERPROFILE%\Documents\cosmo1\train --device auto --strict --save

# то же без GPU и без записи модели (только отчёт)
py -3 tools\train_loop.py --data-dir <путь>\train --device cpu
```

Что происходит по шагам: сначала проверяются конфигурации ёмкости модели (число деревьев, листьев,
пикселей на чип), затем наборы признаков (23 базовых против 40 расширенных), затем:

* **веса «трудных» отрицательных примеров** — пиксели класса 0 на пашне, степи и открытой почве
  получают повышенный вес (на этих покровах 66 % ложных срабатываний, фенологический dNBR неотличим
  от слабого горения);
* **бэггинг по сидам** — лучшая конфигурация обучается три раза на разных подвыборках пикселей,
  вероятности усредняются;
* **пространственная постобработка вероятностей** — усреднение по окружению (3×3/5×5) и фильтр
  большинства по карте классов: убирает одиночные пиксели другого класса внутри пятна гари;
* **понижение класса у мелких пятен** — пятно класса 3 из нескольких пикселей не бывает сильным
  выгоранием: такие пятна переводятся в класс 2 (перебираются пороги 16 и 24 px);
* **ансамбль разных моделей**, смещения классов, морфология маски и переобучение лучшей конфигурации
  на всех чипах;
* **бинарная голова «гарь / не гарь»** — поверх лучшей конфигурации обучается вторая модель на
  тех же пикселях, отвечающая только на вопрос «горит или нет»: её вероятность пересобирает
  многоклассовые вероятности (P(0) = 1 − P(гарь), классы 1–3 делят P(гарь) в прежней пропорции).
  Слабое разделение гари и фона — главный источник ошибок на пашне и в степи, и отдельная голова
  учится на нём целиком, вместо того чтобы делить ёмкость с классами силы выгорания;
* **тюнинг правил активного горения** — пороги самого детектора (`k_sigma`, `delta_day`,
  `candidate_t4`, `delta_night`, `min_cluster_px`) подбираются координатным подъёмом по F1 на одной
  половине AF-чипов (не более 120 чипов, по 60 на половину) и принимаются, только если улучшение видно
  на второй. Это 35 % итогового Score, и раньше их цикл не настраивал; F1 до и после считается на всех
  AF-чипах с эталоном, шаг занимает несколько минут.

Каждый шаг сравнивается с лучшим результатом по объективу `0.35·IoU_burn + 0.30·mIoU_sev`; «не лучше» —
нормальный результат, он просто не принимается. Найденные сглаживание, фильтр большинства и смещения
классов записываются в файл модели, поэтому инференс воспроизводит ровно ту конфигурацию, что выиграла
на отложенной части.

Как читать вывод. Строка шага — это метрики на отложенных чипах (те, что модель не видела) и вердикт
«ЛУЧШЕ / не лучше» относительно лучшего принятого шага. Рядом печатаются обе **половины** отложенных
чипов: улучшение, видное только на одной половине, помечается как неподтверждённое — на 56 чипах
разница до ≈0.01 Score это шум, а не прирост. Флаг `--strict` такие улучшения отклоняет. В конце:

* **честное сравнение** — «было → стало» на отложенной части и рост проекции Score: это и есть ожидаемый
  прирост на платформе (F1 активного горения берётся из `docs/numbers.json`, а если сработал шаг тюнинга
  правил AF — из замера на всех AF-чипах после тюнинга);
* **модель для сабмита** — переобучение лучшей конфигурации на всех BS-чипах (224): качество на
  отложенной части у неё завышено, потому что эти чипы она видела, это помечено в отчёте;
* таблица «шаг → проекция Score» со временем каждого шага.

Самый дорогой шаг — постобработка вероятностей (сглаживание и фильтр большинства): в нём нет
обучения, но перебираются комбинации и под каждую заново подбираются смещения классов. Сейчас он
устроен двухступенчато (точный замер всех комбинаций с текущими смещениями, затем подбор смещений
только для трёх финалистов, причём на поиске морфология не считается) — на 56 отложенных чипах это
десятки секунд вместо четверти часа. Если и этого много, шаг убирается целиком: `--no-spatial`.

Если ни один шаг не подтвердил улучшения, цикл пишет об этом прямо и **не трогает файлы в `weights`**:
на сабмит остаётся прежняя модель из весов. Это защита от худшего сценария с `--strict` — иначе цикл
мог бы записать конфигурацию первого шага, которая хуже исходной.

Сравнить готовые модели без обучения (какая из них лучше на одних и тех же чипах):

```bash
py -3 train.py --data-dir <путь>\train --eval-model weights\severity_model.pkl
py -3 train.py --data-dir <путь>\train --eval-model weights\severity_model.prev.pkl
```

Печатаются метрики BS на отложенной части (честные) и на всех чипах (оптимистичные, зато сравнимые
между собой и с тем, что уходит на платформу) плюс проекция Score. Так видно, какая модель дала тот или
иной результат на платформе, а не по памяти.

**Если веса перезаписаны** (например, `train.py` запустился с испорченным путём и нашёл 0 чипов —
в старых версиях он в этом случае писал пустой `weights.json`): модель берётся из
`weights\severity_model.prev.pkl` (её сохраняет цикл), пороги и режим — из `weights\weights.json`
репозитория (после первого прогона с новым кодом есть и копия `weights\weights.prev.json`). Проверка,
что конфигурация верная:

```cmd
py -3 train.py --data-dir "<путь>\train" --eval-model weights\severity_model.pkl
```

На 56 отложенных чипах должно быть `IoU_burn≈0.5391`, `mIoU_sev≈0.5146` — это и есть та модель,
что дала на платформе 0.6979.

Важно: с `--save` в `weights/` записывается именно модель для сабмита (обученная на всех чипах), прежняя
остаётся рядом как `weights/severity_model.prev.pkl`, а прежние веса — как `weights/weights.prev.json`.
Вернуться к прошлой конфигурации — это две команды:

```cmd
copy /y weights\severity_model.pkl weights\severity_model.loop.pkl
copy /y weights\severity_model.prev.pkl weights\severity_model.pkl
rem и, если менялись пороги/морфология: copy /y weights\weights.prev.json weights\weights.json
``` Если модель собирали с xgboost, для инференса xgboost тоже нужен (он уже будет
установлен, раз GPU-путь использовался).

Флаги: `--device auto|cpu|cuda` (по умолчанию `auto`), `--gpu-report` (что известно про CUDA и выйти),
`--cycles N` (ограничить число шагов),
`--pixels` (пикселей на чип; больше — чуть лучше и заметно дольше), `--val-chips N` (ограничить
отложенную часть, отладка), `--f1-af` (зафиксировать F1 для проекции Score), `--report путь`
(куда писать отчёт, по умолчанию `docs/severity_loop.json`), `--quick` (быстрая проверка
работоспособности: меньше пикселей и чипов, все шаги на месте), `--strict` (принимать только улучшения,
подтверждённые обеими половинами отложенных чипов), `--af-tune/--no-af-tune` (тюнинг порогов детектора
активного горения, включён по умолчанию), `--save` (записать модель и правила AF в `weights/`);
`--eval-model путь` — это флаг `train.py`, сравнение моделей без обучения.

Ориентиры по времени: на двух ядрах полный прогон — 20 минут, на шести ядрах без GPU — около 8–10 минут,
с CUDA — единицы минут (обучение ускоряется, метрика считается на CPU).

Отчёт о прогоне сохраняется в `docs/severity_loop.json`: конфигурации, метрики каждого шага и время.

### 2.3. GPU: что ускоряется и как включить

GPU ускоряет только **обучение** модели степени поражения (на 12-ядерном CPU один цикл занимает
десятки секунд, с CUDA — секунды), на метрику это не влияет. Инференс решения GPU не требует: он
параллелится по процессам, а число потоков внутри процесса решение нормирует само (ядра / процессов),
поэтому рост `--jobs` не упирается в переподписку ядер. На бытовом 6-ядерном CPU (12 потоков) разумный
запуск — `--jobs 12`: набор из 269 чипов на 6-ядерной машине при восьми процессах считался 37 с, при
двенадцати по расчёту (те же 0.14 с на чип на процесс) укладывается в лимит 30 с — за него в критериях
дают 8 баллов скорости (5 минут — 6 баллов, 12 минут — 4, 30 минут — 2).

**Шаг 1 — драйвер.** `nvidia-smi` должен показать карту (для RTX 3060 — 12 ГБ) и версию драйвера.
Если команда не найдена, поставьте драйвер NVIDIA: без него CUDA-путь не заработает.

**Шаг 2 — xgboost.** Сборка из PyPI умеет CUDA, отдельный «gpu»-пакет не нужен:

```bash
py -3 -m pip install --upgrade xgboost
py -3 -m pip install nvidia-cuda-runtime-cu12    # если драйвер есть, а CUDA-рантайма нет
py -3 -c "import xgboost; print(xgboost.build_info()['USE_CUDA'])"   # ожидаем True
```

**Шаг 3 — проверить, что GPU реально виден решению.** Сборка с CUDA ещё не значит работающая CUDA:
xgboost молча уходит на CPU, если не нашёл устройство. Поэтому проверка идёт пробным обучением и
чтением конфига бустера:

```cmd
py -3 train.py --gpu-report
py -3 tools\train_loop.py --data-dir %USERPROFILE%\Documents\cosmo1\train --gpu-report
```

Отчёт печатает состояние драйвера (`nvidia_smi`, `gpu`, `driver`), каталоги CUDA-библиотек внутри
Python (`cuda_dll_dirs`) и проверку, какие библиотеки реально загружаются (`cuda_libraries`). Откат на
CPU определяется по сообщениям самого xgboost («No visible GPU is found…», «Device is changed from GPU
to CPU»), а подтверждением работы GPU служит GPU-структура `ellpack` в его же логе: проверка только по
конфигу бустера давала ложный минус на исправной карте (xgboost 3.4 не пишет фактическое устройство в
`save_config`). Разбор ответа:

* `runtime_ok: true` и `"устройство": "cuda"` — GPU-путь готов;
* `runtime_ok: false`, `nvidia_smi: null` — **драйвера нет или он не в PATH**: это и есть причина, никакие
  pip-пакеты её не исправят. Поставьте/обновите драйвер NVIDIA, перезагрузитесь;
* `runtime_ok: false`, драйвер виден и версия есть — не хватает CUDA-библиотек: `py -3 -m pip install
  --upgrade xgboost nvidia-cuda-runtime-cu12 nvidia-cublas-cu12 nvidia-cuda-nvrtc-cu12`. Каталоги этих
  пакетов решение подхватывает само (`cuda_dll_dirs`), в путь их добавлять вручную не нужно;
* `runtime_ok: false`, а в `cuda_libraries` всё «загружается» — смотрите `reason`: там дословное
  сообщение xgboost (например, о несовместимости версии рантайма с драйвером);
* в поле `reason` печатается и предупреждение самого xgboost (например, о несовпадении версии рантайма с
  драйвером) — оно обычно точнее любых догадок.

Переключатель — флаг `--device`:

* `--device auto` (по умолчанию) — GPU, если он реально доступен, иначе CPU;
* `--device cuda` — требовать GPU: если его нет, скрипт напечатает причину и продолжит на CPU;
* `--device cpu` — принудительно CPU (sklearn-бэкенд, без xgboost).

Тот же переключатель есть у `train.py` (`--device`, плюс `--backend sklearn|xgboost` и
`--features base|ext`) и у `inference.py`/`evaluate.py` (`--device` — где считать уже обученную
модель; по умолчанию там, где обучена). Модель, обученная на GPU, читается и считается на CPU —
xgboost хранит только структуру деревьев, поэтому решение остаётся переносимым.

Что меняется на GPU: все обучающие шаги цикла идут через xgboost (`tree_method="hist"`), включая те,
что на CPU выполнялись sklearn-бустингом, поэтому **числа могут немного отличаться от CPU-прогона** —
это разные реализации, а не ошибка. Цикл сравнивает шаги между собой на отложенных чипах и записывает
то, что выиграло, так что на его выбор это не влияет.

Ориентиры по времени: на 6 ядрах без GPU полный цикл занимает ≈30 минут (замер участника — 1875 с),
с CUDA — единицы минут: время уходит на обучение моделей, а не на сбор признаков.

**Время инференса и баллы за скорость.** Цикл оставляет в файле модели ансамбль (несколько моделей,
вероятности усредняются) — это прибавка к качеству и потеря к скорости. Замеры на 269 чипах: одиночная
модель при `--jobs 12` укладывалась в лимит 30 с (8 баллов за скорость), ансамбль из трёх моделей
считает тот же набор ≈90 с (6 баллов, порог 5 минут). Если скорость важнее двух баллов — оставьте в
`weights/` прежнюю одиночную модель (`severity_model.prev.pkl`) или обучите цикл с `--cycles 8`; если
важнее метрика (Score — основной критерий кейса) — оставьте как есть.

## 4. Ответ для организаторов (главная команда)

```bash
python inference.py --data-dir ~/firesdata/test --output submission.csv --validate
```

**На платформу грузится именно `<data-dir>/submission.csv`** — не `sample_submission.csv` (в нём одни пустые
строки, это шаблон организаторов: платформа примет его и поставит почти нулевой Score).

* `--validate` сверяет результат с `sample_submission.csv` (если он найден рядом) и проверяет формат;
* печатает время, число чипов и строк;
* детерминирован: повторный запуск даёт побайтово одинаковый файл.

Проверка файла ответа без эталона (формат, полнота, RLE, правдоподобие относительно обучающей части):

```bash
python tools/check_submission.py --data-dir ~/firesdata/test --submission submission.csv
```

Итоговый Score на тесте локально посчитать нельзя — нужны скрытые маски организаторов, оценку даёт платформа
после загрузки файла. `check_submission.py` ловит грубые сбои (пустой ответ, «горит половина чипа», пропущенные
пары, битый RLE) и сравнивает статистику с прогоном на обучающей части.

Проверки перед загрузкой (то же делает `--validate`):

1. шапка ровно `chip_id,class_id,rle`, разделитель — запятая;
2. `rle` — серии отсчётов с 1, без пересечений и пропусков внутри строки;
3. все `chip_id` из шаблона присутствуют (AF — `class_id` 0/1, BS — 0–3);
4. время прогона < 30 с на полный тест.

## 7. Windows (cmd.exe) — те же шаги, без bash

Кавычки в путях: `--data-dir "C:\Users\Вы\Documents\cosmo1\train"` — кавычки одинарные, без
удвоения. Запись вида `--data-dir ""C:\...\train" --eval-model ...` cmd склеивает в один аргумент,
флаг теряется, и решение обучается на несуществующем каталоге. С новым кодом такой запуск просто
останавливается с сообщением «каталог не найден» и не трогает веса.

Команды — одной строкой в `cmd.exe` (не в Git Bash: `cd /d`, `\` в путях). Python вызывается как `py -3`.
`<путь>` ниже — папка, внутри которой лежат `af\` и `bs\` (в каждой свой `meta.csv`); найти её можно так:

```bat
dir /s /b %USERPROFILE%\Documents\*meta.csv
```

```bat
cd /d %USERPROFILE%\Documents\cosmo1\solutions\fires-monitoring
py -3 -m pip install -r requirements.txt
py -3 -m pytest tests -q

rem обучение (≈40–70 мин на i5-11400F; обучающая часть: 420 AF + 224 BS чипа)
py -3 train.py --data-dir <путь>\train --out weights\weights.json

rem проверка на обучающей части (метрика соревнования и вклад механизмов)

py -3 evaluate.py --data-dir <путь>\train --ablation > ablation.txt

rem GPU-обучение (необязательно) и цикл из 17 шагов с отчётом «до и после»

py -3 tools\train_loop.py --data-dir <путь>\train --device auto --save

rem ответ организаторам

Грузить на платформу — файл `submission.csv` из папки `solutions\fires-monitoring`

## 8. Что держать в голове по метрике (из Q&A с организаторами)

* **Очаги (AF) и контуры гари — то, что оценивается**; точность верификации точки возгорания — нет.
  Поэтому основной вес в работе — на AF и BS, а не на «объяснении» факелов.
* **Разметка степени поражения сделана по порогам dNBR** (экспертная проверка — выборочная), то есть
  пороговый подход — не упрощение, а ровно то, как построен эталон.
* **Полигон теста тот же** (Нижнее Поволжье и Подонье), климатические зоны не смещаются: пороги,
  подобранные на train, переносятся.
* **Пиксели под облаками оцениваются «как есть»**. Маскировка по SCL у нас подтверждена на эталоне
  организаторов (+0.02 IoU_burn, +0.015 Score): под облаком наблюдения недостоверны, и предсказание там не
  улучшает, а портит метрику.
* В тесте есть приватная часть; состав не раскрывается, поэтому никаких «подгонок под лидерборд»:
  все параметры подобраны только на train-части.
* Разрешено считать локально или в облаке (Colab, Yandex Cloud) — решение не требует GPU и работает
  на CPU, что и есть самый быстрый вариант развёртывания «здесь и сейчас».
